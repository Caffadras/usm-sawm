# Лаба 04: защита конфиденциальных данных

За основу взята гостевая книга из лабы 3. К ней добавлена таблица `user`.
Пароль каждого пользователя записан тремя способами: открытым текстом, в MD5
и в Argon2id. Так все три способа видно в одной строке.

Три колонки пароля нужны только для демонстрации. Настоящее приложение хранит
одну колонку: `password_hash`.

## Запуск

Нужен PHP 8 с PDO SQLite и поддержкой Argon2id. Из корня проекта:

```sh
php -S 127.0.0.1:8000 -t lab04
```

Откройте <http://127.0.0.1:8000>. При первом запросе создаётся файл
`lab04/guest.sqlite` с таблицами `guest` и `user`. В таблицу `user`
добавляются шесть пользователей. Чтобы начать заново, удалите этот файл.

Первая загрузка идёт около 3 секунд, потому что Argon2id медленный нарочно.

## 3. Уязвимость: пароли в открытом виде

Колонку `password_plain` может прочитать любой, кто получил доступ к базе:

- злоумышленник после SQL-инъекции (лаба 2) или кражи резервной копии;
- администратор базы или разработчик;
- любой, кто увидит логи или дамп базы.

Люди часто используют один пароль на многих сайтах. Поэтому одна утечка даёт
доступ и к почте, и к банку пользователя. Такая атака называется credential
stuffing: украденные пары логин и пароль пробуют на других сайтах.

## 4. Как составлять и хранить пароли

**Составлять:**

- Длина важнее сложности. Нужно не меньше 12–15 символов.
- Хороший вариант: фраза из нескольких случайных слов. Четыре или пять слов
  надёжнее, чем три.
- Свой пароль для каждого сайта. Удобно хранить их в менеджере паролей.
- Не брать имя, дату рождения, слова из словаря, раскладку клавиатуры.
- Включить двухфакторную аутентификацию, если сайт её поддерживает.

| Слабые | Почему |
|---|---|
| `123456`, `qwerty`, `password` | в начале каждого словаря паролей |
| `Ivan1990` | имя и год рождения легко угадать |
| `P@ssw0rd` | замену букв на символы словари тоже знают |

| Надёжные | Почему |
|---|---|
| `Kp7#vQ2!mZ9$wL` | 14 случайных символов разных типов |
| `лампа-ветер-сосна-окно-38` | длинная фраза из случайных слов, легко запомнить |

**Хранить** (на стороне приложения):

- Никогда в открытом виде.
- Никогда не шифровать обратимо. Ключ лежит на том же сервере и утечёт вместе
  с базой.
- Только медленная хэш-функция с солью: Argon2id, bcrypt, scrypt или PBKDF2.

## 5. Почему MD5 и SHA1 считаются уязвимыми

1. **Они быстрые.** Их создали для проверки целостности файлов, где скорость
   нужна. Для паролей скорость помогает атакующему. Видеокарта считает
   десятки миллиардов MD5 в секунду. Даже PHP на обычном процессоре этого
   компьютера считает около 7,7 млн MD5 в секунду и только около 6 Argon2id.
2. **У них нет соли.** Один пароль всегда даёт один хэш. Хэш `123456` в MD5
   всегда `e10adc3949ba59abbe56e057f20f883e`. Его можно найти поиском в
   интернете.
3. **Найдены коллизии.** Коллизия: два разных входа с одинаковым хэшем. Для
   MD5 их находят с 2004 года, для SHA1 с 2017 года (атака SHAttered).
   Коллизии опасны в первую очередь для подписей и сертификатов. Для паролей
   главные проблемы — первые две.

**Атаки на пароли в MD5:**

- **Словарная атака.** Посчитать MD5 списка частых паролей и сравнить с базой.
- **Полный перебор (brute force).** Перебрать все комбинации символов. При
  такой скорости короткие пароли перебираются за минуты.
- **Радужные таблицы и готовые базы «хэш → пароль».** Их строят один раз
  заранее и используют для любой утёкшей базы. Это работает только без соли.
- **Одинаковые хэши.** В базе видно, у кого одинаковый пароль. Взломал один,
  получил всех. В демо это `alice` и `dave`.

## 6. Применение Argon2id

```php
// регистрация
$hash = password_hash($password, PASSWORD_ARGON2ID);

// вход
if (password_verify($password, $hashFromDatabase)) { ... }
```

`password_hash()` сама создаёт случайную соль. `password_verify()` достаёт соль
и параметры из сохранённой строки. Отдельно хранить соль не нужно.

## 7. Почему Argon2id, как он хранится, зачем соль

**Почему Argon2id.** Он победил в конкурсе Password Hashing Competition в 2015
году. OWASP рекомендует его первым. Он медленный, и ему нужно много памяти.
Видеокарта не может запустить тысячи попыток сразу: у неё мало памяти на
каждое ядро. У bcrypt одна попытка занимает около 4 КБ памяти, у Argon2id в
PHP по умолчанию 64 МБ. bcrypt тоже допустим, а MD5 и SHA1 нет.

**Как он хранится.** Пример строки из колонки `password_hash`:

```text
$argon2id$v=19$m=65536,t=4,p=1$QnhTUGhhN0ZPVTZSaEtGZg$qruSBQoJ77WuBoHrgMNfvOp+ePRrXLIFPmaxX8gBMN4
```

| Часть | Значение |
|---|---|
| `argon2id` | алгоритм |
| `v=19` | версия алгоритма |
| `m=65536` | память: 65536 КБ = 64 МБ |
| `t=4` | число проходов |
| `p=1` | число потоков |
| `QnhTUGhh...` | соль, 16 случайных байт в base64 |
| `qruSBQoJ...` | сам хэш |

**Преимущество хранения в виде хэша.**

- Из хэша нельзя получить пароль обратно. Утечка базы не раскрывает пароли
  сразу.
- Атакующему нужно перебирать пароли, и каждая попытка стоит дорого.
- Приложению открытый пароль не нужен: при входе оно хэширует введённый
  пароль и сравнивает результат.

Хэш не делает слабый пароль сильным. `123456` найдут и в Argon2id, но
намного медленнее и для каждого пользователя отдельно.

**Роль соли.** Соль — это случайная строка. Она своя для каждого пароля и
добавляется к нему перед хэшированием.

- Одинаковые пароли дают разные хэши. В таблице у `alice` и `dave` пароль
  `123456`, MD5 одинаковый, а Argon2id разный.
- Заранее построенные таблицы «хэш → пароль» становятся бесполезны. Их
  пришлось бы строить заново для каждой соли.
- Атакующий не может перебирать пароли всей базы сразу. Каждого пользователя
  приходится атаковать отдельно.

Соль не секрет. Она хранится открыто, рядом с хэшем. Её задача — сделать
каждый хэш уникальным. Скрывать её не нужно.
